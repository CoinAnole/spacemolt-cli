# Docs issues

Complaints about cached gameserver docs versus what the CLI has to render.
Live server captures were not taken. The CLI design for these entries used
`spacemolt-docs/openapi.json`, `spacemolt-docs/changelog.json` 0.632.4, and
the prose files cited below.

## find_route `route` is described as null and typed as an array

- Spec: `spacemolt-docs/openapi.json`, OpenAPI 3.1.0, schema `FindRouteResponse`.
- `found.description`: "False means no path was found; route is then null and the fuel fields are 0."
- `route.description`: "Null when found is false."
- `route.type` is `array`. `route` is in `required`. The property has no `nullable` and `type` does not include `null`.
- `additionalProperties` on `FindRouteResponse` is false.
- Changelog `0.632.4` (2026-10-17): "`route` is `null` and the fuel fields are 0 when no route is found."
- The 200 example `structuredContent` is a found route with a three-step array. It does not show `route: null`.
- Gap: a client that validates the schema rejects the null the descriptions require. A client that trusts the type never renders the not-found shape the changelog describes.
- CLI behavior meanwhile: human output treats `route: null` as not found, and prints fuel fields that are present, including 0. The high-value fixture stays a schema-valid found route so the fixture-schema baseline does not grow a type-mismatch row for this.
- Live capture: not taken. Collecting a real not-found body is out of scope for this CLI change.

## find_route wormhole execution prose lags the 0.632.4 field descriptions

- `RouteStep.via_wormhole.description`: "Take it by jumping to entrance_poi (jump target_system in v1, id in v2) from the previous step's system. Omitted means a normal jump to system_id."
- `RouteStep.entrance_poi.description`: "POI ID of the wormhole entrance, in the previous step's system, that leads to this step. Present only when via_wormhole is true."
- Changelog `0.632.4`: "A step with `via_wormhole: true` is reached by jumping to its `entrance_poi`, which is in the previous step's system."
- Operation `POST /api/v2/spacemolt/find_route` description still says: "execute those hops with jump({target_system}) from anywhere in the entrance system."
- `spacemolt-docs/docs/travel.md` (Wormholes bullet under Moving Between Systems): "`find_route` marks those hops with `via_wormhole: true` and an `entrance_poi`; execute them with a normal `jump` from anywhere in the entrance system."
- `spacemolt-docs/docs/exploration.md` (Wormholes): "you execute them with an ordinary `jump` from anywhere in the entrance system."
- Those three prose sentences name a `jump` of the destination system from anywhere in the entrance system. The field descriptions and the first 0.632.4 note name a `jump` whose v2 `id` is `entrance_poi` in the previous step's system. That contradiction is the complaint. It does not depend on the example-response note below.
- Observation, separate from that contradiction: the 200 example route steps include `system_id`, `name`, and `jumps` only. The example does show `fleet_fuel` arithmetic (`6 × 2 = 12`, `9 × 2 = 18`, `14 − 18 = -4`) and a negative `fuel_on_arrival`. It does not show `via_wormhole`, `entrance_poi`, or `route: null`. The `find_route` note itself does not say the example shows those three.
- Changelog `0.632.4` has six notes. The sixth note, after the facility-list notes, is its own sentence: "The example responses for both commands now show realistic data that follows these rules." "Both commands" is not named in that sentence. It may mean `find_route` and `facility action=list`, or only the facility notes above it. This complaint does not treat that sentence as a promise that the `find_route` example shows wormholes or `route: null`.
- CLI behavior meanwhile: help says a wormhole step is a jump to `entrance_poi` in the previous system, which is the field description and the first 0.632.4 note. Human output prints `via_wormhole` and `entrance_poi` on the step. The CLI does not try to decide whether the ship must be at that POI or may jump it from elsewhere in the system.
- Live capture: not taken.

## `jump` id description does not mention a wormhole entrance POI

- Operation `POST /api/v2/spacemolt/jump` description: "A wormhole entrance POI ID in your system is a valid target once you have charted it; an uncharted entrance is an unknown system (unknown_system)."
- Request property `id` description on that operation, in full (`openapi.json` line 49032): "ID of the adjacent system to jump to (use get_system to see connected systems), or a numeric compass bearing in degrees for an off-network Pathfinder Drive jump. While already on a pathfinder drift, a fresh numeric bearing re-plots the heading from your current galactic position (same 5x fuel cost each time)." The full property description does not mention a POI id. The operation description at line 49021 does.
- `RouteStep.via_wormhole.description` says the v2 jump field is `id`, and the value is `entrance_poi`.
- The example body is `{"id":"system_id"}`.
- Gap: the operation prose allows a charted wormhole entrance POI id, and the parameter prose allows a system id or a bearing. A generator that shows only the parameter description hides the POI target.
- CLI behavior meanwhile: `find_route` help tells the reader to jump to `entrance_poi`. This complaint does not change `jump` help. `jump` help already says an uncharted wormhole entrance returns `unknown_system` (`src/command-overrides-core.ts`).
- Live capture: not taken.

## `fleet_fuel` changelog wording is easy to read as "leader row only"

- Changelog `0.632.4`: "The `fleet_fuel` rows (leaders only) include your own ship, and a negative `fuel_on_arrival` means that member runs out of fuel on the way."
- `FindRouteResponse.fleet_fuel.description`: "Per-member fuel check over this route, yourself included. Present only when you lead a fleet with more than one member and a route was found; members without a ship are skipped. Omitted otherwise."
- `FleetMemberFuel.fuel_on_arrival.description`: "Negative means the member runs out on the way."
- The parenthetical "leaders only" matches the schema if it means "this array is sent to fleet leaders." It also reads as "the array contains only the leader." The schema says the array includes the leader and the other members who have a ship.
- The 200 example includes two rows (VegaDrift and OreHauler7), which matches "yourself included" plus another member, and a negative arrival on the second row.
- CLI behavior meanwhile: help uses the schema sentence (lead a fleet of more than one member, rows include your ship, shipless members skipped). The table prints every row in the array. A negative `fuel_on_arrival` is printed with its minus sign. Help says that negative means that ship, including yours, runs out on the way.
- Live capture: not taken. No session was opened to see a one-member fleet, a shipless member, or a follower's `find_route`.

## `guides/fuel.md` find_route planning section names fields and arguments the v2 schema does not have

- `spacemolt-docs/guides/fuel.md` section "Using find_route for Planning" shows `find_route(to_system="Sol", to_poi="Sol Central")` and lists a return field `arrival_tick` ("Estimated completion time") beside `estimated_fuel`, `fuel_per_jump`, and `fuel_available`.
- Cached v2 `POST /api/v2/spacemolt/find_route` request body is one required string, `id`: "Destination system ID, POI ID, or station Base ID."
- `FindRouteResponse` properties are `cargo_used`, `estimated_fuel`, `fleet_fuel`, `found`, `fuel_available`, `fuel_per_jump`, `message`, `route`, `target_poi`, `target_poi_name`, `target_system`, `total_jumps`. There is no `arrival_tick`.
- `spacemolt-docs/api.md` line 832 is one bullet: `find_route(target_system)` — "Find the shortest route to a destination system, POI, or base".
- `spacemolt-docs/skill.md` has two mentions. Line 345, under exploration tips: "Use `find_route` to plan routes between systems." Line 371 is the tool bullet, the same `find_route(target_system)` sentence as `api.md`. Neither line names `via_wormhole`, `entrance_poi`, `route: null`, `estimated_fuel`, `fleet_fuel`, `arrival_tick`, `to_system`, or `to_poi`. That is thinner than the 0.632.4 field descriptions. `api.md` and `skill.md` are lag by omission next to the fuel-guide contradiction. They do not assert the fuel guide's call shape.
- `spacemolt-docs/docs/travel.md` does name `fuel_per_jump`, `estimated_fuel`, `fuel_available`, and `cargo_used`, which matches the operation description. Its wormhole sentence is the separate complaint above.
- CLI behavior meanwhile: the command stays positional `target_system` aliased to wire field `id`. Human output prints the fuel fields the schema defines. It does not print an arrival tick.
- Live capture: not taken.

## Checked, and not filed as a separate defect

- Generated CLI metadata `POST /api/v2/spacemolt/find_route` in `src/generated/api-commands.ts` copies the request summary and the `id` description. It has no response-field descriptions. `scripts/generate-api-metadata.ts` stores request metadata. That is CLI generator scope, not a gameserver doc defect.
- `FindRouteResponse` integer fields can still arrive as `bigint` inside this CLI when `parseApiJson` sees a token outside the safe integer range. The OpenAPI type remains `integer`. The CLI prints the `bigint` with `formatIntegerText`. No gameserver doc change is requested for that.
- `estimated_fuel` "0 when you are already there" and `fuel_per_jump` "at least 1" except when `found` is false or the caller has no ship are consistent: a found route of `total_jumps` 0 can show per-jump fuel above 0 and estimated fuel 0. The formatter prints both numbers as sent.

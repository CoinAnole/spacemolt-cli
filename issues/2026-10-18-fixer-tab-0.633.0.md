# Docs issues

Spec and documentation gaps found while designing SpaceMolt CLI behavior. Each entry is a complaint, not a gameserver change request that this CLI can close. The CLI design that depends on these entries is `/tmp/grok-spacemolt/grok-design-doc-2ec2e17f.md`. No live server responses were collected.

Docs stamp while reading: `spacemolt-docs/changelog.json` `current_version` **0.637.3**. Bundled CLI metadata `GENERATED_API_GAMESERVER_VERSION` is **v0.637.3**. The fixer-tab behavior itself is gameserver **0.633.0** (release date 2026-10-17 in that changelog).

## 2026-10-18 — V2 player has no fixer_debt; legacy Player does

**Sources**

- `spacemolt-docs/openapi.json` schema `Player` has `fixer_debt` ("Zero or omission means no debt") and `fixer_deliveries` ("Zero or omission means no successful deliveries"). `Player.additionalProperties` is unset.
- The only `$ref`s to `Player` are `LoggedInPayload.player`, `LoginResponse.player`, and `RegisterResponse.player`.
- `get_status`, `get_player`, and `get_active_missions` all return `structuredContent` as `V2GameState`. `V2GameState.player` is `$ref` `V2Player`. `V2Player` has `additionalProperties: false` and no `fixer_debt` or `fixer_deliveries`.
- `V2GameState.missions` is `V2Missions`, which has optional `fixer` → `FixerAccountInfo` (`debt`, `allowance`, `exposure`, `available`). Description: omitted when no player exists.
- `spacemolt-docs/api.md` and `spacemolt-docs/skill.md` (section "Fixer debt and restitution") say mission responses and `get_state` include the account, cargo allowance, and current exposure. They do not say `player.fixer_debt` is on the v2 status or `get_player` blob.
- `POST /api/v2/spacemolt/get_player` description lists identity, credits, faction, stats, `arena_xp`, and `arena_won`. It does not mention fixer debt or missions.
- `POST /api/v2/spacemolt/get_status` description says it is an alias of `get_state` and returns the full state blob, including `missions`.

**Uncertainty**

A spec-compliant `get_status` / `get_player` body has the shared account on `missions.fixer` only if that command populates `missions`, and has no `player.fixer_debt`. Whether the live server still copies `fixer_debt` onto the v2 player object is unknown. `V2Player.additionalProperties: false` says it must not.

**What the CLI will do**

Human output prints `player.fixer_debt` when that key is present. On `get_status`, `get_state`, and `get_player` only, if that key is absent, it falls back to `missions.fixer.debt`. It does not print `fixer_deliveries`. `--json` stays the raw payload. See the design doc for the zero-debt rule.

## 2026-10-18 — Active missions omit cargo_liability; board rows have it

**Sources**

- `MissionInfo` (the `get_missions` row) has optional `cargo_liability` and `restitution_relief`.
- `ActiveMissionInfo` has `restitution_relief` and does **not** have `cargo_liability`.
- `GetMissionsResponse.fixer` and `V2Missions.fixer` are both `FixerAccountInfo`. `fixer` is not in `GetMissionsResponse.required` (required are `missions`, `base_name`, `base_id`) and not in `V2Missions.required` (required are `active`, `max_missions`).
- `POST /api/v2/spacemolt/get_missions` description says the fixer account is shared, `cargo_liability` reserves allowance, and restitution jobs advertise `restitution_relief`.
- `POST /api/v2/spacemolt/get_active_missions` description is only "Returns active missions and max mission count in the v2 state envelope." It does not mention fixer, liability, or relief, even though the state blob's `missions` schema includes `fixer` and active rows include `restitution_relief`.

**Uncertainty**

It is unclear whether a live active-mission row ever includes `cargo_liability`, or whether `get_active_missions` always populates `missions.fixer`. The changelog line "Mission views show your balance" does not name the command.

**What the CLI will do**

`get_missions` prints the account when `fixer` is present, and optional Liability / Relief columns when a row actually has those integers. `get_active_missions` prints `missions.fixer` when present and the same optional columns. A missing key does not become 0. No live call will be added to decide this.

## 2026-10-18 — storage deposit positional order disagrees with OpenAPI

**Sources**

- `POST /api/v2/spacemolt_storage/deposit` request schema sets `x-positional-index` 0 on `target`, 1 on `item_id`, and 2 on `quantity`. The same indexes are copied into `src/generated/api-commands.ts` (`positionalIndex` on that route).
- Curated `storage_deposit` in `src/command-overrides-commerce-facility.ts` sets `positionals: ['item_id', 'quantity', 'target', ...]`. `mergeCommandConfig` in `src/commands.ts` uses curated positionals when they exist, so the CLI parses `storage deposit <item_id> <quantity> [target]`.
- Generated `target` description (not overridden) already says `fixer:tab` accepts `item_id=credits` and a positive quantity. Curated `schemaExtensions.item_id.description` **replaces** the generated `item_id` text, and the replacement does not mention `fixer:tab`. Curated command description also does not mention it. `command-metadata.test.ts` requires the curated `item_id` text to keep the tow-rig sentences, so a fixer sentence has to be appended, not swapped back to the generated paragraph.

**Uncertainty**

None about which order the CLI executes. The uncertainty is only which order a reader of the raw OpenAPI will type.

**What the CLI will do**

Help will document the curated argv, `storage deposit credits 500 target=fixer:tab`, and will not follow OpenAPI positional 0. This design does not regenerate metadata and does not change positional order. `target=fixer:tab` and item id `credits` will be reserved so the id cache cannot rewrite them.

## 2026-10-18 — credits= versus item_id=credits for the fixer tab

**Sources**

- Changelog **0.633.0**: ``send_gift recipient="fixer:tab" credits=500``.
- `spacemolt-docs/api.md` and `spacemolt-docs/skill.md`: v1 form is that `send_gift`; v2 form is `storage action="deposit" target="fixer:tab" item_id="credits" quantity=500`.
- Deposit operation description matches the v2 form (`item_id="credits" quantity=500`).
- Deposit field `credits` description: amount to gift a player; "Faction credit deposits use item_id='credits' with quantity instead." It does not mention `fixer:tab`.
- There is no `send_gift` CLI command. Storage is grouped; users type `storage deposit`.

**Uncertainty**

Whether the server also accepts the `credits` integer field when `target` is `fixer:tab` is not stated. The operation text and the v2 sentence in api.md name `item_id` and `quantity` only.

**What the CLI will do**

Help will tell users to pass item id `credits` and a quantity, not `credits=`. The CLI will not remap `credits=` into `quantity` when the target is `fixer:tab`. There will be no `send_gift` command.

## 2026-10-18 — missions.md and storage.md lag the 0.633.0 tab

**Sources**

- `spacemolt-docs/docs/missions.md` abandon paragraph: provided goods still in the hold are confiscated, and "you are charged the base value of any you no longer carry. Only delivery pays." No shared fixer account, restitution job, or `fixer:tab`. The board section does not mention `cargo_liability` or `restitution_relief`.
- `spacemolt-docs/docs/storage.md`: the two credit exits it names are `faction_deposit_credits` and `send_gift` to a player, faction, or empire. No `fixer:tab`. It also says item and credit gifts require a base with storage service, which api.md says is **not** required for a fixer payment.
- `spacemolt-docs/guides/mission-runner.md` has no fixer-debt section.
- OpenAPI `abandon_mission` description: missing courier cargo becomes persistent fixer debt at base value even if the wallet is empty. Expiry uses the same rule. Settle with `send_gift recipient=fixer:tab` or restitution jobs.
- `FixerAccountInfo.exposure`: moving or selling the provided cargo does not release exposure. `docs/missions.md` does not say that.

**Uncertainty**

`docs/missions.md` can be read as an immediate wallet charge ("you are charged", "Only delivery pays"). The OpenAPI and changelog say the charge is shared debt that survives an empty wallet, and that jobs abandoned before 0.633.0 are not charged. Story missions "keep their replacement-stock terms" (changelog 0.633.0). `AcceptMissionResponse.replacement_cost` exists and is a different field from `fixer`.

**What the CLI will do**

Human copy will follow the OpenAPI and changelog: debt, not a wallet charge, and payment via `storage deposit` with item id `credits`. The CLI will not edit `spacemolt-docs`. It will not print `replacement_cost` as if it were fixer debt.

## 2026-10-18 — No error code for a rejected tab payment

**Sources**

- Component enums in `spacemolt-docs/openapi.json` were searched for fixer, restitution, and debt. The only debt-like enum hit was `ShippingDebtPaymentResponse.action` = `pay_debt`, which is freight, not the fixer tab.
- Deposit and `send_gift` descriptions say payment is capped at debt and wallet, that items, ships, faction funds, and bulk entries are rejected, and that the sender must be at an empire station with mission services. They do not name the error `code` for those rejections.

**Uncertainty**

The wire code for "not at a mission station", "nothing owed", "bulk entries", or "wrong item" is unknown.

**What the CLI will do**

No new entries in `src/errors.ts`. Existing generic errors stay as they are. The cap and the station requirement go in `storage deposit` help only.

## 2026-10-18 — FixerAccountInfo integers are unconstrained

**Sources**

- `FixerAccountInfo` properties `debt`, `allowance`, `exposure`, and `available` are `type: integer` with examples `[2000]`, `[5000]`, `[3000]`, and `[2000]`. No `minimum`, `maximum`, or `format`.
- `debt` text says zero means no outstanding debt. `available` text says zero means no additional unsecured cargo. `Player.fixer_debt` says zero or omission means no debt.
- Required array is all four fields, but every response that embeds `fixer` says omission of the object means no snapshot. A present object is therefore assumed to carry all four, but the CLI cannot know that older or partial payloads do.

**Uncertainty**

Negative debt, a float, a numeric string, or a present object missing `debt` are all outside the examples. No live payload was captured.

**What the CLI will do**

Only a finite number or bigint is displayed. Strings are not coerced. Null, objects, and arrays are skipped. An explicit 0 is kept inside a fixer account block and hidden on the single status/player debt line. A non-zero negative number is printed as sent so a bad value is visible. Omitted keys are not filled in.
